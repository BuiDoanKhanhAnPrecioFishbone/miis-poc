1. Modelling principles
The information model is strictly based on the Mediation Office’s own data model (Appendix A) and the concept definitions in Appendix 1 §4.2. Appendix A explicitly states that the fields are "examples and not exhaustive" and that fields will be added – the model is therefore built for extensibility. Where the requirements force structures that Appendix A does not show, entities have been added; these are marked with an asterisk (*) in the diagram and motivated in the entity catalogue. Six principles govern the design:
One agreement per party pair (§4.2): each row in Agreement represents an agreement between one employer organisation (AGO) and one employee organisation (ATO). The Agreement area groups agreements with different parties.
Separate validity periods: Wage agreements and General terms are separate entities with their own signing dates and validity periods (FA-004), with Wage revision and Minimum wage as subgroups of the Wage agreement (§4.2).
System versioning for snapshots: the central entities (Agreement, WageAgreement, GeneralTerms, Party) are temporal tables, which provides the snapshot function (FH-003) and complete version history without a separate archive solution – a query with FOR SYSTEM_TIME AS OF reconstructs the state as of any date.
Business history separated from technical history: party name changes (FP-004) are handled in PartyNameHistory with business validity dates, so that current agreements show the current name while historical agreements resolve the name against the agreement’s time period. System versioning is a separate, technical layer.
Polymorphic support entities: Document and EventLog are linked via entity type + entity id to all relevant entities, exactly as Appendix A specifies ("linked to all agreement tables, Negotiation, Party meeting, Mediation").
Append-only traceability: the ChangeLog (old/new value, FH-001/NFL-002) is protected against modification and deletion even for the system administrator (NFL-003) via permissions and triggers, and is retained for at least 24 months.
2. Information model (logical level)
The model comprises 34 entities in five domains: Parties and organisation, Reference data and shared, the Agreement domain, Negotiation/party meeting/mediation, and Documents/AI/traceability. Stage 2 entities (grey, dashed) are part of the model from the start so that the data model accommodates them – but they go live in Stage 2. Physical table names are Swedish; the key columns (*_id) shown in the figure map directly to the DDL script.

4. Key design decisions and trade-offs
4.1 Snapshots via temporal tables
Requirement FH-003 ("reconstruct how the data looked on a specific date") is realised with SQL Server’s system-versioned tables on Avtal, Loneavtal, AllmannaVillkor and Part. A report as of 31 December runs as an ordinary query with FOR SYSTEM_TIME AS OF – no separate archive database, no snapshot jobs, and the version history is produced automatically on every change. This complements the change log: temporal tables give the row’s full state per point in time, while the change log gives the field-level who/when/what traceability (NFL-002).
4.2 Party names and organisational changes
FP-004 requires that name changes propagate to current agreements but not historical ones. The solution: Agreement references part_id (a stable identity); the current name is taken from Party; for historical views and snapshots the name is resolved via PartyNameHistory against the requested time period. Mergers (Sveriges Lärare, Fremia) are handled as new parties with relationships to their predecessors via CooperationBodyMember/PartyNameHistory, preserving statistical continuity.
4.3 Confidentiality in the data model
Confidentiality (D-001) exists on both Agreement and Document, since the requirement states that the marking applies "primarily" to attached documents while agreement details must also be hidden (D-002). Public views and the mediator role’s views filter on the flag; statistics views aggregate including confidentiality-marked agreements. Filtering happens in the database view layer plus the application’s RBAC (NFÅ-003/004) – dual protection.
4.4 Polymorphic links for Document and EventLog
Appendix A explicitly states that Document and EventLog are linked "to all agreement tables, Negotiation, Party meeting, Mediation". The alternative – one FK column per target table – yields a sparse and hard-to-extend structure. We follow Appendix A’s intent with entity type + entity id and secure integrity in the application layer plus the IX_Dokument_Entitet index. The trade-off (no declarative FK) is documented deliberately.
4.5 Stage 2 in the schema from day one
PensionAgreement, OtherAgreement, the link tables and SignedBy are created already in the Stage 1 schema but without UI. The reason is the migration strategy: the data model must accommodate the historical Access information from the start (NFM-002), and the relationships to Agreement/Party/CooperationBody must not require schema rebuilds in Stage 2 (cf. question 3.2 in the question list to MI). OtherAgreement in basic form is moreover used already in Stage 1 for the negotiation procedure agreements (FA-006/FA-017), which drive the mediation flow (FF-006).
4.6 Derived colour coding
The colour coding (FR-012) is never stored but derived: red when a MediationAgreement link exists or the agreement was signed after mediation, green for newly signed without mediation, blue for remaining agreements. This guarantees consistency – the status can never be "forgotten" when a mediation link is created.
5. Physical database schema
The complete T-SQL script is delivered separately as MIIS_databasschema.sql and comprises five schemas (Swedish names, matching MI’s domain language):
gemensam (shared) – parties, cooperation bodies, reference data, users/roles, saved searches
avtal (agreement) – the agreement domain including the Stage 2 tables
medling (mediation) – negotiation, party meeting, coordinated demands, mediation (special/standing), mediators
dok (documents) – documents with full-text index (Swedish, LCID 1053) and watchword hits
logg (log) – event, change, login and e-mail logs (append-only)
The script contains requirement references in the comments per table, CHECK constraints for controlled value sets (agreement construction 1–7, the eight roles, report selection types, SignedBy exclusivity), a starting index set for the search patterns, and implementation notes for snapshots, confidentiality views, colour coding, retention jobs and migration staging (an etl schema).
Open points that depend on MI’s answers to the question list: the exact fields for "Märket" (question 4.6), data volumes for sizing (3.4), and the SQL Server version and licensing model in Försäkringskassan’s vDC (1.4) – temporal tables require SQL Server 2016+ and full-text search requires the Full-Text Search component to be installed in the operating environment.
